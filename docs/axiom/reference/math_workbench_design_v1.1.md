## 0. 决策摘要

本产品不应该被定义为“可以写公式和画矩阵的电子白板”，而应定义为：

> **一个以结构化数学表达式为程序，以可追踪执行图为骨架，以二维/三维观察器为窗口，并且让每个计算步骤都能被检查、调试和重放的本地数学工作台。**

它与传统计算器的差别不只是多一个动画，而是全程维持同一份可执行语义：用户编辑的公式、运行时对象、执行记录、梯度记录和视觉表示都能通过稳定 ID 互相定位。计算层不依赖 DOM；渲染层不负责数学求值；动画层不反向改写计算状态。

### 建议立即冻结的 10 项架构决策

1. **公式不是 LaTeX 字符串本身。** LaTeX 是重要的输入/输出表示；内部使用带类型、可序列化、可版本化的数学中间表示（Math IR）。
2. **流程图不是计算引擎。** 流程图编辑器修改工作流图；执行引擎接收经验证的不可变执行计划；渲染器消费执行事件和 Presentation IR。
3. **采用三层核心模型：Math IR → Execution IR/Trace → Presentation IR/Animation Plan。** 这三层共享稳定 ID 和版本号，但不共享 UI 对象引用。
4. **Rust/WASM 负责数值热点，TypeScript 负责产品编排。** 先实现可测试的 CPU 数值内核；按需启用 WASM SIMD、Web Workers 和后续 GPU 后端，不把 WebGPU 当作首发硬依赖。
5. **自动求导与前向执行图共用操作语义。** 每个算子单独登记形状推断、数值执行和 VJP/JVP 规则；调试器观察同一计算图的前向值、反向伴随量和梯度。
6. **FP4/MXFP4 等低精度必须被准确标注为格式/量化策略，不与 FP64 组成简单的单轴“精度等级”。** 低精度能力需区分存储编码、输入格式、块缩放、累加格式和后端是否原生支持。
7. **视觉上以“从上向下的前向计算层”为主线。** 反向传播使用明确的反向梯度轨道或上行箭头；循环在概览层折叠、单步调试时局部展开；不可为了视觉顺滑而歪曲真实执行顺序。
8. **二维平铺和三维层叠是同一执行语义的两个视图。** 视图切换不重跑计算；选择一个矩阵格或执行节点时，公式、表格、节点和时间线共同高亮。
9. **本地项目使用可迁移的单文件项目格式，内核可导出开放 JSON/二进制数据。** 建议以 SQLite 文件作为 `.mathproj` 项目容器，另提供可读的 JSON/ZIP 导出与 Git 友好交换格式。[S12]
10. **免费不等于没有治理。** 所有核心能力免费、无需登录、不强制云端；采用对商业和社区友好的开源许可证，并建立依赖许可证清单、贡献规范、版本化插件 API 与可持续赞助机制。

### 首个完整体验闭环

用户拖入 `A`、`x` 和矩阵乘法算子，自动形成 `y = Ax`；系统为未赋值符号生成明确标注的示例数据；点击“运行”后可看见输入、中间乘积和输出；切换到三维层叠视图时，每一步沿 Z 轴分层；点选某一步可检查 shape、dtype、耗时、输入和输出；打开自动求导后，系统展示 `\partial L / \partial A` 与 `\partial L / \partial x` 的反向轨迹；全部步骤可以逐步执行、暂停、回退、重播并导出 trace。

## 1. 产品定位与目标边界

### 1.1 产品愿景

让数学从“写出来的符号”变成“可执行、可拆解、可验证、可观察的结构”。使用者不必先成为程序员才能运行一个算法，也不必只看一张最终结果图才能理解计算过程。专业用户则可以进入类型、精度、算子实现、执行 trace 和梯度规则，获得可复现的工程可调试性。

### 1.2 目标人群

| 人群 | 核心任务 | 关键成功体验 |
|---|---|---|
| 数学/计算机学生 | 理解矩阵运算、分解、梯度、算法步骤 | 公式与中间值同步变化；可拖拽构建与逐步执行 |
| 教师与内容作者 | 构造可交互的讲解、示例、可重复课程材料 | 模板可复制；运行结果可锁定；项目离线可携带 |
| 工程师/研究者 | 检查形状、数值稳定性、精度与算法行为 | 可复现 trace、断点、比较不同 dtype/算法、导出数据 |
| AI/ML 开发者 | 理解 tensor 运算、前向与反向传播 | 梯度图、计算图、权重/激活观察器、ONNX 导入的扩展空间 |
| 开源贡献者 | 增加算子、算法模板、观察器或内核后端 | 明确的算子注册协议、测试夹具、版本兼容策略 |

**设计建议：** 在同一项目里支持“引导模式”和“专家模式”，而不是做两个产品。引导模式只隐藏复杂度，不改变数学语义；专家模式揭示类型、dtype、内存、梯度、性能和运行时警告。

### 1.3 产品差异化

1. **数学语义可见：** 公式不是静态排版，而是引用变量、数据对象、算子和算法模板的结构化对象。
2. **过程可见：** 中间结果、输入输出端口、迭代、梯度和精度转换都有观察器。
3. **表示可替换：** 同一份结果可由公式视图、矩阵平铺视图、数据流视图和 3D 层叠视图消费。
4. **调试是产品能力而不是开发者彩蛋：** 每个函数都有输入夹具、单步执行、输出快照、断点、日志和动画回放。
5. **离线优先：** 无账号也能创建、编辑、计算、调试、导出项目；无网络依赖是可测试的产品目标。

### 1.4 非目标（首发阶段）

- 不宣称首发就完整替代 MATLAB、Mathematica 或 Maple 的所有符号计算、专业工具箱和生产工程能力。
- 不把 3D 视图做成“所有数据都必须进入三维空间”的强制模式。
- 不允许运行时任意插件直接接触 DOM、文件系统或主进程权限。
- 不承诺在所有 GPU 上原生执行 FP4、FP8 或任意量化格式。
- 不在 MVP 中做云同步、团队协作、在线账户、商业云算力或平台内模型商店。

### 2.3 建议的商业/开源定位

- 个人、学生、教师、研究者、商业用户均可免费下载和离线使用核心功能。

## 3. 产品功能蓝图

### 3.1 一级模块

1. **项目空间（Project Workspace）**：项目、页面、输入数据、计算图、运行历史、版本/检查点、导入导出。
2. **公式构建器（Formula Builder）**：LaTeX 输入、结构化公式编辑、拖拽符号、类型占位符、公式组块组合、表达式诊断。
3. **数学对象检查器（Object Inspector）**：标量、向量、矩阵、张量、集合、函数、索引、单位/元数据、shape/dtype、数据范围。
4. **算法画布（Algorithm Canvas）**：由公式块、数据块、控制流块、循环、条件分支组成的可执行工作流。
5. **观察器（Observers）**：单步输入输出、矩阵格、张量切片、数值分布、特征、梯度、精度转换、运行时性能。
6. **二维/三维可视化（Views）**：公式、矩阵/张量平铺、节点图、Z 轴层叠、时间线/动画回放。
7. **调试控制台（Debug Console）**：独立调用函数、输入夹具、断点、watch、step/continue/reverse、trace 导出、断言和基准测试。
8. **公式仓库（Formula Library）**：可版本化的公式定义、类型约束、出处、示例参数、测试夹具和引用。
9. **算法仓库（Algorithm Library）**：公式组合 + 可执行实现 + 可视化策略 + 复杂度说明 + 正确性测试。
10. **精度实验室（Precision Lab）**：FP64、FP32、FP16、BF16、FP8、FP6、FP4/MXFP4、整数与量化策略的表示、误差和后端能力对比。
11. **自动求导工作台（Autodiff Studio）**：前向图、反向图、梯度、JVP/VJP、梯度检查、反向传播状态机。
12. **后续数学模块**：微积分、偏导与梯度、最优化、排序/图算法、统计、神经网络推理与训练流程。

### 3.2 首发功能优先级

| 优先级 | 功能 | MVP 验收内容 |
|---|---|---|
| P0 | 项目和本地保存 | 新建/保存/恢复项目、自动保存、撤销重做、项目导出 |
| P0 | 数学对象和类型系统 | Scalar/Vector/Matrix/Tensor 基础 shape 与 dtype 推断；类型不匹配时明确报错 |
| P0 | 公式编辑与拖拽组块 | LaTeX 输入，结构化表达式，符号 palette，操作模板拖入、占位符吸附 |
| P0 | 算子注册和运行时 | 加法、乘法、矩阵乘、转置、求和、ReLU、平方、sin/exp 等基础算子；单步执行 |
| P0 | Trace 与调试器 | 每步输入/输出/shape/dtype/status/耗时；断点、watch、步进和回放 |
| P0 | 2D 平铺观察器 | 矩阵乘法中间乘积/累加可视化；行列与元素联动高亮 |
| P0 | 可折叠 Z 轴层叠 | 每个执行步骤一层；层折叠、选中步骤、跨层依赖链接和视角控制 |
| P0 | 自动求导基础 | 对基础算子生成反向模式 VJP；损失函数到输入的梯度；梯度检查 |
| P1 | 算法模板仓库 | 矩阵乘法、线性方程组、LU/QR、梯度下降的模板与测试 |
| P1 | 精度实验室 | FP64/FP32 为基准；FP16/BF16/FP8/FP4 的编码/量化模拟与误差对比 |
| P1 | 偏导与 Jacobian | 多输入标量函数梯度、向量函数 Jacobian；展示计算图与梯度流 |
| P2 | 大型张量和高性能后端 | 基准测试后引入 SIMD/线程/GPU 后端，并保留稳定 CPU fallback |
| P2 | ONNX 导入、脚本接口与神经网络模型图 | 先推理再评估训练；所有导入图仍能映射到标准 IR |
| P2 | 排序/图算法及最优化全家桶 | 按通用 IR 与 trace API 扩充，不给各领域另造一套可视化系统 |

**强提醒：** 你选择了“首版纳入自动求导”，这意味着 P0 不是只做演示动画。必须有数学算子契约、可自动测试的 VJP/JVP 规则和数值梯度检查，不然只是视觉上“像”自动求导。

## 4. UX/UI 工作台布局

### 4.1 主窗口默认布局

建议采用单主窗口 + 可停靠面板的 IDE 式工作台。默认参考尺寸为 **1440×900**；在较窄屏幕中允许左侧资源栏折叠、右侧检查器转为弹出面板、底部控制台收纳为抽屉。

├───────────────┬───────────────────────────────────────────────┬──────────────────────┤

### 4.3 左侧符号网格

符号库不是一张无语义的 Unicode 字符表，而是有类别、数学含义、默认类型、快捷键和插槽行为的对象目录：

- **原子与常量：** `0`, `1`, `e`, `\pi`, `i`, `\infty`, 布尔/逻辑常量。
- **数据对象：** 标量、向量、矩阵、张量、集合、函数、分布、索引、参数。
- **算子：** `+`, `-`, `\times`, `\cdot`, `\otimes`, 转置、逆、范数、点积、矩阵乘法。
- **结构与控制：** 求和、乘积、分段函数、循环、条件、映射、过滤、归约。
- **微积分/优化：** `\partial`, `\nabla`, Jacobian、Hessian、梯度下降、链式法则。
- **神经网络：** Linear/Dense、Activation、Softmax、Loss、Normalization、Attention（后续模块）。

每个网格项有 `symbolId`、`displayLatex`、`semanticType`、`inputPorts`、`defaultTemplate`、`dragPolicy` 和 `documentationRef`。拖动向公式上放时，系统按目标插槽类型提供吸附提示，不在没有类型匹配时静默拼接。

### 4.4 公式搭积木的交互规则

1. **输入方式并存。** 支持 LaTeX 键入、公式键盘、符号网格拖入、从仓库拖入完整公式模板和复制粘贴。
2. **视觉结构与语义结构分离。** MathLive 可承担成熟的数学输入交互 [S10]，但外部同步维护内部 AST；不能仅靠解析屏幕上的字符定位公式组件。
3. **类型化占位符。** 例如 `A \in \mathbb{R}^{m\times n}`、`x \in \mathbb{R}^{n}`；拖入矩阵乘法后，系统从 shape 推断出输出为 `m` 维向量。
4. **局部组块。** 一个公式块可以暴露一个或多个输入端口和输出端口，被另一个公式块消费；内部可折叠，但可以进入局部公式编辑器。
5. **错误早反馈。** 维度冲突、缺失输入、非法 dtype、未定义变量或不可微操作以文本提示 + 端口标记显示；不把“计算失败”推迟到最后一步。
6. **符号化和示例值分开。** 无输入值时，默认显示数学占位符；用户可以点击“用示例数据预览”，此时使用确定性、易读的小型数据（例如 2×2 矩阵），明确标为“示例数据”，不得伪装成用户真实输入。
7. **可追溯。** 选中公式中的符号，会高亮左侧变量定义、相关对象、计算图节点和 trace 中的具体执行实例。

### 4.5 公式视图与信息结构视图联动

对于 `y = Ax + b`，公式画布显示严谨的数学符号；右侧/旁侧的结构视图显示 `matmul(A,x)` → `add(...,b)` 的操作结构；矩阵观察器显示每个矩阵和向量的值及维度；3D 视图显示每步的结果层。点击任一处都必须通过 `nodeId/valueId/stepId` 联动，而不是靠屏幕坐标猜测对应关系。

### 4.6 默认符号配色系统

建议以**语义类型**而非变量名字着色，且色彩不是唯一信息通道。示例 token：

| 语义类别 | 建议色相（示例） | 辅助编码 |
|---|---|---|
| 常量/固定参数 | 石墨灰 | 圆角 token + `const` 标签 |
| 标量/实数变量 | 琥珀色 | `scalar` 类型标记 |
| 向量 | 青绿色 | 一维长条/箭头图标 |
| 矩阵 | 蓝色 | 网格图标；行列标签 |
| 高阶张量 | 靛蓝/紫色 | 多层切片图标；rank 标签 |
| 函数/可调用对象 | 紫色 | 函数括号/λ 图标 |
| 索引/维度变量 | 绿色 | 下标/轴标签 |
| 运算符 | 中性前景色 | 操作类型符号/端口连接 |
| 梯度/伴随量 | 洋红或专用强调色 | 反向箭头 + `grad` 标签 |
| 精度转换/量化节点 | 橙红强调色 | 显示输入/输出 dtype 与缩放块 |

实际色值需在浅色/深色主题、色觉缺陷模拟和投影环境中测试。矩阵格的数值高低可使用连续色阶，但**语义色和数值色不能混为一套颜色规则**。给用户提供色盲友好方案，允许修改主题，但保留语义类别图例。

### 4.7 首次运行的引导

第一次打开时提供 3 个项目入口：`跟着示例学习`、`从空白项目开始`、`打开现有项目`。教学示例从 `向量加法`、`矩阵乘法`、`线性方程组`、`求函数梯度` 中选，避免启动后给出空白画布和一大片不明按钮。每个内置示例都可重置、逐步运行、查看数学解释和打开真实执行图。

## 5. 二维平铺与三维层叠可视化

### 5.1 两种视图共享同一数据源

**二维平铺视图**适合观察矩阵格、卷积窗口、排序序列、归约、元素级算子与特征分布。它强调局部位置、行列、滑动窗口、每个输出元素的来源和累加路径。

**三维层叠视图**适合观察程序的前向执行层、张量流、算法迭代、神经网络层和中间结果的时间/依赖关系。每个执行步骤在 Z 轴上对应一个“执行层片段”；层可折叠、展开、锁定或单独聚焦。

两者都只消费 `Presentation IR` + `Animation Plan`。视图切换不能重新执行数学函数，除非用户显式修改参数或点击重新运行。

### 5.2 Z 轴层叠模型

- **顶部：输入层。** 变量、数据集、参数与明确的 dtype/shape 标签。
- **中间：执行层。** 每个算子或算法步骤对应一层或一个可折叠小组；层内可显示公式、节点、输入输出端口和局部矩阵。
- **底部：输出层。** 最终值、损失、分类/特征分布、误差与状态摘要。
- **传递关系：** 数据流从上往下，边连到消费对象的端口；一个值被多个下游消费时呈现分叉/广播，不复制“假的”源数据对象。
- **循环：** 概览里将 5 次迭代表现为一组 `×5` 的折叠轨道；展开后显示第 1…5 次的实际 trace 实例和每次不同的状态。视觉上可用回边表达控制流，但执行时间线仍保留严格的顺序编号。
- **局部回送：** 通过有标签的回边连至上游依赖，并在下方时间线标识实际发生顺序。不要将回边误绘为“同时发生”的新层。
- **反向传播：** 前向值沿主要 Z 方向向下；反向梯度采用专门的反向色彩/箭头轨道向上回传。若只画向下流，将会误导用户对真实反向模式的理解。
- **高维属性：** 不制造“第四条垂直坐标轴”。三维空间表示空间位置或计算层；超过三个维度的量用属性（颜色、透明度、标签、纹理、切片、分面或统计摘要）表达，并明确标出映射规则。例如 4D/5D 张量的每个切片在层标签上显示索引，不能把甜味或颜色等属性伪装成新空间轴。

### 5.3 二维平铺的计算观察

对于矩阵乘法 `C = AB`，选择 `C[i,j]` 后：

1. 在 A 的第 `i` 行和 B 的第 `j` 列高亮参与计算的元素。
2. 以逐项乘法小格显示 `A[i,k] × B[k,j]`。
3. 按累加顺序展示 partial sum；暂停时可看出每次累加前后数值。
4. 在 C 对应单元格显示最终结果。
5. 在公式区标出当前 `i,j,k` 与求和符号；调试器记录每次可观察的子步骤。

对于排序，列表/数组以原始索引和值双标签显示；比较、交换、分区、合并的操作节点显式命名。对于卷积或特征提取，窗口随步长移动，输出特征写入目标位置。

### 5.4 动画与性能规则

- 动画计划是可序列化对象：步骤、目标对象 ID、开始/结束 keyframe、缓动、语义标签和降级策略。
- 计算执行速率与渲染帧率解耦。动画暂停不冻结数学引擎已完成的运行结果；逐步模式则由调试器控制下一条 trace 事件。
- 大矩阵采用采样、虚拟化网格、分块更新或 GPU 绘制，不对每个 cell 创建独立 DOM 元素。
- 动画默认可关闭；提供“快速播放/逐步播放/只看最终结果/减少动态效果”。
- 每一帧不是新的执行记录；执行 trace 与动画帧分离，避免文件大小随帧率无界增长。

### 5.5 图形技术选择

建议 2D 小型/中型矩阵先用 React 虚拟化表格，密集网格用 Canvas/WebGL；流程图先可采用自建的基于 SVG/Canvas 的节点视图，或评估 React Flow 作为编辑器底座。3D 可先用 Three.js，初版默认以稳定的 WebGL 2 路径为主，并把 WebGPU 视为能力探测后的可选后端。Three.js 文档说明 WebGPURenderer 支持 WebGPU 并可回退 WebGL 2，但其仍有实验性边界；MDN 也将 WebGPU 标记为尚未在所有主流浏览器普遍可用。[S11][S13]

## 6. 核心架构：让计算、表示和渲染彻底分层

### 6.1 架构总图

> 原始架构图 `assets/architecture.png` 未随源文档提供；本仓库未伪造该图。请参考原设计稿或后续架构图版本。

### 6.2 三层语义契约

**A. Math IR（数学中间表示）** 描述数学是什么：表达式树/图、符号、单位（后续）、类型约束、变量引用、算子 ID、来源 LaTeX span 和版本号。它不含 DOM、CSS、摄像机位置或动画时间。

**B. Execution IR / Trace（执行中间表示与执行记录）** 描述做了什么：算子、输入值引用、输出值引用、执行实例、顺序、时间、状态、异常、梯度关联。执行计划是可验证的；trace 是具体某次运行的不可变记录。

**C. Presentation IR / Animation Plan（表现中间表示与动画计划）** 描述如何解释/呈现：矩阵格、节点/端口、层级、标签、颜色 token、相机视角、折叠分组、时间轴动作。它不做数学求值，也不得改变 RuntimeValue。

**Renderer（渲染器）** 只负责把 Presentation IR 画出来，并提供交互事件（选中、缩放、折叠、切片选择、播放/暂停请求）。Renderer 不能直接执行矩阵乘法或计算梯度；它将动作转成 UI command，由上层调度器发送给引擎。

### 6.3 关键数据结构（示意 TypeScript）

```ts
type ValueId = string;
type NodeId = string;
type StepId = string;
type DType =
  | "bool" | "i32" | "i64" | "f64" | "f32"
  | "f16" | "bf16" | "fp8-e4m3" | "fp8-e5m2"
  | "fp6" | "fp4" | "mxfp4" | "int8";

interface MathNode {
  id: NodeId;
  op: string;
  args: NodeId[];
  declaredType?: MathType;
  source?: { latex?: string; start?: number; end?: number };
  schemaVersion: number;
}

interface RuntimeValueRef {
  valueId: ValueId;
  kind: "scalar" | "tensor" | "symbolic" | "object";
  shape?: number[];
  dtype?: DType;
  storageRef?: string; // 内存/磁盘句柄，不暴露原始后端指针
}

interface ExecutionEvent {
  runId: string;
  stepId: StepId;
  nodeId: NodeId;
  sequence: number;
  phase: "forward" | "backward" | "control";
  inputs: RuntimeValueRef[];
  outputs: RuntimeValueRef[];
  status: "ok" | "warning" | "error" | "skipped";
  durationNs?: number;
  warningCodes?: string[];
  parentStepId?: StepId;
  iteration?: { loopId: string; index: number; count?: number };
}

interface PresentationNode {
  id: string;
  kind: "formula" | "matrix" | "tensor-slice" | "op-node" | "layer" | "label" | "edge";
  sourceIds: string[];  // 指向 MathNode / StepId / ValueId
  layout: Record<string, number | string>;
  styleTokens: string[];
  payload: Record<string, unknown>;
}
```

这是逻辑示意而非最终 ABI。真正的生产 schema 需要通过 JSON Schema/TypeScript 类型生成、版本迁移与契约测试固定下来。不要将未经约束的 `unknown` 作为长期持久化协议。

### 6.4 算子注册协议

建议每个算子由相互独立的能力描述组成：

- `OperatorSpec`：稳定 ID、名称、输入/输出端口、参数 schema、类别、版本、数学定义、边界条件。
- `TypeRule`：输入类型/shape 推断、广播规则、输出类型与静态诊断。
- `Kernel`：纯数值/符号执行，接收 RuntimeValue，不访问 UI、DOM 或 Electron API。
- `DifferentiationRule`：单独登记 VJP/JVP 规则；不可微或不连续行为需明确策略。
- `TracePolicy`：定义何时产生事件、是否捕获输入输出快照、是否暴露内部 micro-step。
- `VisualizationAdapter`：独立把 trace 转成 2D/3D Presentation IR；这是 UI 团队可扩展的部分。
- `TestFixture`：标准输入、期望输出、形状、异常条件、梯度检查、精度容差和可重复随机种子。

```ts
interface OperatorSpec {
  id: string;
  version: string;
  ports: PortSchema;
  infer(inputTypes: MathType[], params: unknown): InferenceResult;
  kernel: KernelHandle; // 不能接受 DOM/React 对象
  differentiation?: { jvp?: RuleHandle; vjp?: RuleHandle };
  tracePolicy: TracePolicy;
  docsRef: string;
}
```

**关键边界：** `VisualizationAdapter` 不应被塞进 `kernel`。一个算子可以被 2D 表格、3D 堆栈、纯文本 trace 和无头测试四种消费者使用；各消费者生成不同表示，但计算结果完全一致。

### 6.6 UI 与 Runtime 的通信方式

- UI command 采用强类型消息，如 `RunWorkflow`、`StepForward`、`SetBreakpoint`、`InspectValue`、`CancelRun`。
- Runtime 事件采用 `RunStarted`、`StepEntered`、`ValueProduced`、`GradientProduced`、`WarningRaised`、`RunCompleted` 等事件类型。
- 每次运行附带 `runId`、`projectRevision`、`schemaVersion`；过期运行事件不能覆盖用户修改后的新状态。
- 大型 Tensor 不在 IPC 中复制全量数值；发送 `RuntimeValueRef` 和有限预览，需要时通过专用 read API 获取切片或摘要。
- 运行过程可取消；取消的语义要明确区分“停止后续步骤”“取消当前内核任务”和“仅停止动画”。

## 7. Electron 窗口与进程架构

### 7.1 进程分工

Electron 基于 Chromium 的多进程模型，主进程管理窗口与生命周期，渲染进程负责 UI，并可通过受控 preload/IPC 访问特定桌面能力；Electron 也提供 Utility Process 用于隔离崩溃风险较高或 CPU 密集型的服务。[S14]

| 组件 | 职责 | 禁止事项 |
|---|---|---|
| Main Process | 窗口生命周期、菜单、文件对话框、项目文件锁、升级与应用状态 | 不执行长时间矩阵运算；不把随意 Node API 暴露给 renderer |
| Preload Bridge | 暴露白名单 API，做 schema 校验与最小权限封装 | 不直接暴露原始 `ipcRenderer`、Node `fs` 或任意命令执行 |
| Workbench Renderer | React UI、编辑状态、视图布局、交互反馈 | 不直接写任意文件；不承担大型内核运算 |
| Compute Worker | 启动/持有 WASM 内核、执行可取消任务、收集 trace | 不访问 DOM 或组件实例；不渲染 UI |
| Utility Process（按需） | 项目迁移、导入检查、后台索引、可能崩溃的插件宿主 | 不将项目文件/插件视为可信输入；应验证与限权 |
| Detached Debug Window | 独立控制台/trace 视图 | 不持有第二份可写的权威运行状态；通过 runId 订阅统一数据 |

### 7.2 推荐默认安全设置

- 所有 renderer `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`。
- 设置严格 Content Security Policy；使用自定义安全协议而不是随意 `file://` 内容路径。
- 校验 IPC sender 与每条消息 schema；禁止不受信任内容创建任意窗口或导航。
- 项目、模板与插件均视为数据，不得把项目内的字符串直接 `eval`。
- 第三方算法插件只能调用受限制的 Operator API；如需执行脚本，应在显式用户授权、资源限制、可取消和隔离环境中进行。
- 依赖 Electron 当前安全版本并定期升级；官方安全清单强调上下文隔离、沙盒、CSP、IPC sender 验证和最小暴露面。[S15]

### 7.3 多窗口模型

首版逻辑上使用一个主窗口，辅助窗口作为“可分离的视图”：

1. `WorkbenchWindow`：主工作台，是唯一主要编辑入口。
2. `DebugWindow`：调试控制台/trace，可拖到另一块屏幕；只订阅当前 project/run。
3. `CompareWindow`：精度/算法结果并排比较，接收不可变运行快照。
4. `HelpWindow`：可选本地帮助与模板详情，不加载不受信任的远程代码。

在窗口间共享的是 `projectId`、`runId`、`stepId` 和只读快照引用，不共享 React state。主进程负责窗口创建与生命周期；项目的权威状态由 Project Store/Runtime 服务维护。

## 8. 本地项目文件、公式仓库与版本

### 8.1 项目模型

一个项目应包含：

- 项目元数据、语言和视图布局；
- 公式节点、算子节点、端口和有向边；
- 符号定义、参数、值对象、示例数据；
- 公式/算法模板引用及固定版本；
- 运行设置、断点、Watch 表达式；
- 运行 trace、关键结果快照和测试夹具；
- 资源/图片/数据文件的内容哈希和来源信息。

### 8.2 存储方案建议

建议 `.mathproj` 初期使用 SQLite 单文件数据库容器：项目元数据与图结构存放在结构化表中，常规数值 blob 可放在数据库，超大数据块则以分块附件 + 内容哈希引用；提供“打包导出”把主库和附件组装成可移植包。SQLite 官方专门讨论了将数据库作为单文件应用格式的跨平台、事务和版本兼容优势。[S12]

建议表：`project_meta`、`graph_nodes`、`graph_edges`、`symbols`、`value_blobs`、`template_refs`、`runs`、`trace_events`、`breakpoints`、`assets`、`migrations`。

要点：

- 每次保存以事务提交；自动保存每隔一段时间或在用户停止编辑后触发，并保留最近恢复点。
- 项目 schema 必须版本化，打开旧项目时先备份，再执行迁移；未知的高版本 schema 不能静默写回。
- trace 默认只永久保存关键步骤和用户收藏结果；完整 trace 可单独导出，避免项目无限膨胀。
- 全局公式/算法库与项目引用分开；项目应锁定具体模板版本或保存内嵌副本，防止更新全局库后项目结果悄然改变。
- 提供人类可读的 JSON 交换格式、纯数据导出、以及可审查的项目 manifest；二进制数据库不应该成为唯一的开放接口。

### 8.3 本地优先的边界

“本地优先”意味着离线创建、运行、保存、导出应能独立成立，不是把所有逻辑都放在主进程。自动更新、手动下载模板库、崩溃报告和赞助入口可以在联网时可选启用；默认不上传项目内容、变量、公式、trace 或数据集。

## 9. 数值内核、WASM 与计算后端

### 9.1 推荐分工

- **TypeScript 层：** 数学 AST 解析/转换、工作流验证、执行调度、值生命周期、调试事件、项目集成、后端选择。
- **Rust/WASM 层：** 热点数值运算、张量内存、基础线性代数、精度转换、未来的自动求导核心。
- **Web Worker：** 在主 UI 线程外运行 WASM，避免大矩阵或长 trace 阻塞交互；通过 transferable buffer 或后续受控共享内存传值。
- **WebGPU：** 作为后端能力而不是默认前提；启动时检测能力，失败时透明回退 CPU/WASM。
- **可选 Python 插件（后续）：** 若用户需求证明必要，再评估 Pyodide/外部 Python；Pyodide 能在 WebAssembly 中运行 CPython，并支持 NumPy、SciPy、pandas 等已移植包，但打包体积、启动成本、包支持差异和双运行时管理都需要实测。[S7]

### 9.2 为什么不把整个数学系统都写在 Rust 中

- 公式编辑、交互状态、窗口管理和插件发现更适合 TypeScript 生态。
- Rust/WASM 适合可测量的计算热点，但不应让每次输入字符都触发 JS/WASM 大量细粒度跨边界调用。
- 以批量张量接口为单位跨 WASM 边界，传 `Float32Array`/内存句柄，而非每个标量都调用一次 WASM。
- 核心 IR 与 runtime API 应保持语言无关，后续替换后端时不影响 UI 或项目文件结构。

### 9.3 数值库选择

候选方案是 Rust 的 `nalgebra` 作为基础向量/矩阵与分解能力的起点，它声明支持浏览器/WASM 等目标并使用 Apache-2.0 许可证；但它是否覆盖你要求的稀疏矩阵、大型 GEMM、混合精度和每一步微观可视化，必须以实际基准测试决定。[S16]

**建议不把一个第三方库直接当成产品的数学语义。** 抽象统一的 `Tensor`/`Matrix` API 和后端接口，再将 nalgebra 或未来的其他内核作为实现。算法演示模式和高性能批量模式可以共用语义，但使用不同执行策略。

### 9.4 性能策略

1. 先建立基准：矩阵尺寸 2×2、32×32、256×256、1024×1024；逐步 trace 版与批处理版分开测。
2. 小规模教学计算默认详细 trace；大规模计算默认聚合 trace，并允许用户针对某节点开启局部追踪。
3. 计算时按块调度和可取消；UI 不等待每个子步骤动画完成再计算下个值。
4. 稀疏矩阵、矩阵分解、SVD、卷积等采用专门内核，不把所有操作退化成通用标量循环。
5. 引入 WASM SIMD、线程、WebGPU 前必须有对照测试，记录速度、内存、设备兼容和数值误差，不仅展示理论峰值。

## 10. 精度与数据格式系统

### 10.1 不要把所有格式只做成一个 `dtype` 下拉框

建议把数字表示拆成多个正交维度：

- **元素编码**：FP64、FP32、FP16、BF16、FP8 E4M3/E5M2、FP6、FP4、INT8 等；
- **块缩放策略**：无、每 tensor、每行/每通道、MX block scaling；
- **累加类型**：例如 FP16 输入但 FP32 累加；
- **输出类型与舍入策略**：round-to-nearest-even、饱和、截断等（具体策略由格式规范和内核能力决定）；
- **执行后端**：WASM CPU、WebGPU、未来的原生后端；
- **支持状态**：原生、软件模拟、量化/解量化近似、不可用。

### 10.2 现实技术边界

WebAssembly 核心数值类型包括 `i32/i64/f32/f64`，SIMD 以 `v128` 承载打包数据；不能把 FP4/FP8/MXFP4 理解为所有 Wasm 目标上都存在的原生标量浮点运算类型。[S17]

OCP MX Specification 定义了带共享块缩放因子的 Microscaling 格式，包含 FP8、FP6、FP4 和 INT8 等元素编码；一个 MX 格式需要同时考虑 scale 编码、元素编码和 block size，不是“单个 4-bit 浮点数”就能完整描述的。[S18]

因此，首发的精度界面要敢于标注：

- **原生**：内核具备真实的算术执行能力；
- **软件仿真**：先按指定编码舍入/量化，再由较高精度执行并按规则回写；
- **量化模拟**：用来观察压缩、误差和分布影响，不等价于目标硬件速度；
- **不支持**：当前后端没有该实现。

### 10.3 推荐首发格式矩阵

| 格式/模式 | 首发用途 | 第一阶段执行策略 | 必须显示的信息 |
|---|---|---|---|
| FP64 | 基准、校验和科学计算对照 | Wasm `f64` | 绝对误差、相对误差、数值范围 |
| FP32 | 默认高性能基准路径 | Wasm `f32` | 与 FP64 参考值差异 |
| FP16 | 混合精度实验 | 软件编码 + 明确的转换/累加策略；硬件能力探测后扩展 | 输入、累加、输出 dtype 分开显示 |
| BF16 | 深度学习常见低精度对照 | 软件编码/舍入模拟，测试后端支持 | 指数范围/有效精度的可视提示 |
| FP8 E4M3/E5M2 | 后续 ML/量化实验 | 编码/解码与量化模拟起步 | 缩放策略、溢出/下溢和量化误差 |
| FP6/FP4 | 低位宽压缩和神经网络实验 | 软件编码/量化模拟起步 | 范围、离散级别、误差直方图 |
| MXFP4 | 块缩放实验 | 实现 MX scale + block size + FP4 element 编码；不宣称本机有原生 FP4 算术 | block size、scale、元素值、反量化值 |
| INT8 / 量化整数 | 推理优化实验 | 量化/反量化；可选整数内核 | scale、zero point、饱和比例 |

### 10.4 精度实验室 UX

每个运行节点都能打开“精度面板”：`输入格式`、`权重格式`、`累加格式`、`输出格式`、`scale`、`舍入方式`、`后端`。并排对比 FP64 参考、FP32、低精度结果，显示绝对误差、相对误差、最大误差、RMSE、NaN/Inf 计数和误差分布。量化矩阵也可在 2D 平铺中用离散色级显示，让用户看清压缩导致的变化。

## 11. 自动求导引擎与可视化

### 11.1 推荐自动求导策略

首版以**反向模式自动求导（Reverse-mode AD）**为主，覆盖由多个输入到一个标量损失的常见问题。概念上，在前向计算时保留记录操作历史的 DAG，再从损失节点向输入回传伴随量/梯度；PyTorch 官方文档以类似的计算图方式描述 autograd 的历史与链式法则。[S19]

同时为 `JVP`（Jacobian-vector product）接口预留空间，用于之后处理输入维数少、输出维数多的问题。不要第一版就承诺任意高阶导数、所有控制流、所有线性代数分解都自动可微。

### 11.2 自动求导数据流

> 原始自动求导图 `assets/autodiff.png` 未随源文档提供；本仓库未伪造该图。请参考原设计稿或后续数据流图。

### 11.3 每个算子的梯度契约

算子不仅需要 `kernel`，还需要明确可微规则：

- `vjp(outputAdjoint, inputs, output) -> inputAdjoints[]`；
- 可选 `jvp(inputs, inputTangents) -> outputTangent`；
- 声明不可微、分段可微或需要用户配置的边界；
- 对广播、归约、切片、转置、reshape 等操作定义梯度逆映射；
- 对输入重复使用或分支汇合的情况正确累加梯度；
- 对矩阵乘法等算子有标准规则和测试夹具。

先支持 `add/sub/mul/div/pow/sin/cos/exp/log/relu/sum/mean/matmul/transpose/reshape/slice/concat` 等有限算子集，覆盖课程常见示例和简单 MLP；之后逐步扩大算子覆盖。

### 11.4 梯度可视化设计

- 主视图中 forward 值从输入向输出流动，backward gradient 从损失向输入回传。
- 节点旁可以切换 `value`、`dL/dnode`、`local derivative`、`shape/dtype` 四种标签。
- 用户点选一个梯度时，显示它由哪些下游梯度和局部 VJP 累加而来。
- 对广播/共享输入用多条贡献线显示求和，而不是只显示最终梯度值。
- 用独立的颜色/箭头区分真实数据流与梯度流，且保持色觉可访问性。
- 在二维视图中对张量梯度显示形状、热力图、选定元素的来源；在 3D 中显示反向遍历的状态层。

### 11.5 梯度正确性验证

生产级自动求导必须有测试，不靠动画是否漂亮来验收：

1. **解析测试**：对已知函数检查导数，如 `f(x)=x²`、`sin(x)`、`Ax+b`。
2. **有限差分对照**：在适用范围用有限差分验证 VJP/JVP；靠近不连续点的测试需排除或明确标注。
3. **随机测试**：固定随机种子对小张量生成输入，与可信参考库或独立实现对比。
4. **边界测试**：空维度、广播、重复节点、常量输入、NaN/Inf、ReLU 零点和除零情况。
5. **梯度检查 UI**：用户可选一个输入参数，查看解析/自动梯度与有限差分估计的差异及容差。
6. **版本回归**：每个算子版本存储测试夹具；改变规则需要运行完整回归集。

有限差分不是自动求导的替代品，只是数值验证手段；在不连续点、舍入边界和病态函数附近必须正确解释结果。

### 11.6 可视化自动求导状态机

建议把调试器状态定义为：`Idle → ForwardRunning → ForwardPaused → ForwardCompleted → BackwardRunning → BackwardPaused → Completed/Failed/Cancelled`。事件至少包括 `TapeNodeCreated`、`ForwardValueCommitted`、`BackwardNodeEntered`、`GradientContributionAdded`、`GradientAccumulated`、`GradientCheckFinished`。动画观察器只订阅这些事件并渲染；状态机是引擎/调试域的一部分，不是 React 组件内部状态。

## 12. 调试控制台：所有函数可独立调试

### 12.1 目标

控制台不是只显示 `console.log` 的开发者窗口，而是产品中的可复现数学执行环境。用户可以选择任何一个函数、算子、公式块、算法模板或视觉适配器，输入最小示例，单独执行并查看返回值和表示对象。

### 12.2 三个运行层级

1. **算子级调试**：比如 `matrix.matmul`，提供输入 A/B、检查 shape/dtype、运行、查看结果/异常/耗时。
2. **公式块级调试**：选择 `y=Ax+b` 中的 matmul 子块，只运行这个子图并查看它生成的 Trace 和 Presentation IR。
3. **算法/工作流级调试**：设置断点、Watch 变量、逐步运行、跳过、回退（通过快照/重放实现）、导出 trace。

### 12.3 推荐命令设计（示例）

```text
help
ops.list category=linear-algebra
run matrix.matmul --fixture small-2x2
inspect value:run-42.step-07.output
break node=matmul-3
watch tensor:grad.W
step
continue
replay run-42 from=step-05
render inspect step-07 view=layer-stack
trace.export run-42 format=json
assert output.shape == [2, 1]
benchmark matrix.matmul sizes=32,128,512 dtype=f32
```

命令行是高级入口；图形界面提供按钮和表单，不要求初学者记命令。命令参数使用语法树解析，不直接 `eval` 用户字符串。

### 12.4 可视化适配器调试

除了调试数学算子，也必须调试用户最重视的“表示对象”和动画生成：

- 输入固定 trace fixture；
- 单独运行 `VisualizationAdapter`，输出结构化 `Presentation IR`；
- 检查节点 ID、边、层次、端口、颜色 token、折叠 group、keyframe；
- 在预览区切换 2D / 3D，并显示 IR inspector；
- 比较两版输出的结构差异（snapshot diff）；
- 用独立 renderer 测试同一 IR 是否稳定绘制。

这样图形/UX 工程师无需每次重跑内核即可调整视觉编码；数学工程师无需操纵 DOM 即可检查计算结果。

## 13. 公式仓库与算法模板仓库

### 13.1 公式仓库条目

每条公式模板建议包含：

- `formulaId`、版本、名称、分类、语言/本地化标题；
- LaTeX 显示形式与 Math IR；
- 输入符号、类型约束、shape 约束和默认参数；
- 输出类型与可能的错误条件；
- 输入输出端口和推荐观察器；
- 解释/推导/引用来源；
- 示例数据和自动测试夹具；
- 相关算子/公式/算法依赖及许可证/出处。

初始分类：线性代数、矩阵分解、数值方法、微积分、优化、概率统计、排序与图算法、神经网络、数值精度。

### 13.2 算法模板条目

算法模板不只是代码片段；它应当是一个可运行的工作流组件包：

`公式组块 + Operator 引用 + 工作流 DAG/控制流 + 参数 schema + trace 策略 + 观察器 preset + 测试夹具 + 复杂度说明`。

例如“梯度下降”模板同时呈现目标函数 `L(θ)`、梯度 `∇θ L`、更新式、学习率参数、每次迭代的 loss 曲线和权重变化。用户可以将它拖入更大的神经网络训练流程，或替换优化器，而不必把公式重新抄一次。

### 13.3 首批模板建议

**线性代数：** 向量/矩阵基本运算、线性方程组、Gaussian elimination、LU/QR、幂迭代、最小二乘、投影、特征值/特征向量。SVD 可以加入模板库，但应在数值稳定性、复杂度和动画粒度通过测试后稳定发布。

**微积分/自动求导：** 链式法则、乘积法则、梯度、Jacobian、梯度下降、有限差分对照。

**算法结构：** 冒泡排序、插入排序、归并排序、快速排序、二分查找、堆、BFS/DFS。算法模板的观察器用数组/树/图视图，不必强行都呈现成矩阵。

**神经网络：** Linear → Activation → Linear → Softmax 的小型推理图；随后加入损失、梯度、优化器状态和反向传播。

### 13.4 模板质量门禁

- 数学定义正确且可引用；
- 输入输出类型、shape 和单位约束清楚；
- 至少有正常、边界、异常三类测试；
- 运行结果确定性足够高，随机部分必须可设种子；
- 说明算法复杂度和数值限制；
- 包含最小可视化 fixture；
- 具备可审查的来源与许可证信息。

## 14. 神经网络扩展架构

### 14.1 模型图与数学公式共用 IR

神经网络中的 Dense/Linear、ReLU、Softmax、Normalization、矩阵乘法、向量归约、loss 和 optimizer 都应是带类型的算子节点。模型定义、公式组合、前向执行和梯度追踪复用同一套 Math IR、RuntimeValue、Execution Trace 和 Presentation IR。

### 14.2 前向与训练视图

- **推理视图：** 输入特征 → 线性变换 → 激活 → logits/概率 → 结果观察器。
- **训练视图：** 前向图、loss、反向梯度、梯度累加、optimizer 更新分为明确阶段。
- **权重观察器：** 显示矩阵/张量切片、数值分布、dtype、shape 和量化scale。
- **反向传播：** 梯度箭头与前向值流分色；折叠每一层，但展开时可查看每个输入/输出梯度。
- **性能视图：** 计算时间、内存占用、后端、批大小、精度模式。不要把 GPU 理论峰值当作实测性能。

### 14.3 ONNX 和已有生态

建议先提供 ONNX 模型导入和前向推理，不要一开始承诺完全兼容所有训练图。ONNX Runtime Web 支持 WebAssembly CPU 执行提供程序，并提供 WebGPU 等执行提供程序；其官方兼容矩阵显示不同浏览器/平台支持程度存在差异，WebGPU 在某些组合下不支持或有限，因此必须保留 CPU/WASM fallback。[S8]

导入的外部模型需映射为内部可检查的节点；无法映射的算子应以“黑盒外部算子”显示，并标注不可展开或不可求导的边界，而不是假装已经支持。

## 15. 2D/3D 表示对象与动画 API

### 15.1 Presentation IR 设计原则

1. **描述性而非命令式。** 表示“这个节点是什么、在哪里、有哪些端口和语义样式”，不是“在 DOM 元素上执行 translate”。
2. **可序列化、可重放。** 相同的 trace + 视觉配置应生成同样的结构对象。
3. **与计算引擎无关。** 算子实现不需知道 2D/3D 或具体渲染库。
4. **稳定 ID。** 一个数值可以对应同一源变量、运行值、流程节点和多个视图中的投影。
5. **大数据可渐进加载。** 先显示 shape、摘要和切片预览；只有用户展开时才读取大块数值。

### 15.2 动画计划示意

```ts
interface AnimationPlan {
  runId: string;
  viewId: string;
  steps: Array<{
    stepId: string;
    targetIds: string[];
    action: "highlight" | "move" | "reveal" | "transform" | "collapse" | "annotate";
    startMs: number;
    durationMs: number;
    easing?: "linear" | "ease-in-out";
    semanticLabel?: string;
    reducedMotionFallback?: "instant" | "highlight-only";
  }>;
}
```

动画计划与执行 trace 分开储存。用户拖慢播放速度不改变数值；视觉适配器可以生成一个动画视图的计划，但不能重新跑内核，也不能通过回调直接修改源张量。

## 16. 开源、免费与长期可持续性

### 16.1 建议的许可证策略

这是需由项目负责人最终决策的法律/治理问题，本文给工程建议而非法律意见。

- **核心应用与自研计算库：** 优先评估 Apache-2.0 或 MIT。Apache-2.0 提供明确的专利授权条款；MIT 更简洁。若希望社区可以广泛复用、企业容易集成，两者都常见。要在“尽可能允许复用”与“希望衍生版本回馈社区”之间明确取舍。
- **数学公式/算法模板内容：** 评估 CC BY 4.0 或与软件相容的内容许可，并保留来源、作者和引用元数据。
- **依赖治理：** 维护 SPDX/SBOM，发布依赖许可证清单；重点审查 GPL/LGPL、字体、数据集、公式文本、图标与模型权重的再分发条件。
- **插件 API：** 定义版本兼容策略、能力权限清单、包签名/哈希验证与隔离运行模式。

可借鉴的依赖：MathLive 官方仓库标注 MIT 许可；`nalgebra` 官方文档说明其 Apache-2.0 许可；CortexJS Compute Engine 提供 MathJSON 语义表达、LaTeX 解析/序列化及符号/数值计算能力。[S10][S16][S20]

### 16.2 免费产品的可持续模式

| 模式 | 建议 | 说明 |
|---|---|---|
| 自愿赞助/捐赠 | 适合早期 | 不影响所有功能免费；公开资金用途和路线图 |
| 社区/科研资助 | 适合中期 | 以数学教育、可解释计算、可复现科研为申请主题 |

## 17. 工程质量、测试与发布

### 17.1 测试金字塔

- **单元测试：** Math IR 构建/解析、shape/type 推断、算子 kernel、梯度规则、精度编码、动画计划。
- **属性测试：** 矩阵转置两次回到原形、`A(I)=A` 等适用性质、形状推断 invariant、序列化往返、模板引用稳定性。
- **数值对照：** FP64 参考、小矩阵已知解、独立梯度实现/有限差分、边界值与误差容差。
- **集成测试：** `公式编辑 → IR → Run → Trace → Presentation IR → Renderer` 的完整闭环。
- **视觉回归：** 固定 trace fixture，比较 2D/3D 视图截图与节点/关键帧 snapshot。
- **跨平台 E2E：** 首发门禁覆盖 Windows/macOS 的文件打开保存、快捷键、GPU fallback、升级和异常恢复；Linux 先保持构建/CI 冒烟与社区预览，正式支持前补齐全套回归。
- **安全测试：** 恶意项目文件、超大数据、循环资源消耗、未授权 IPC、第三方插件崩溃与非法输入。

### 17.2 MVP 验收标准（建议）

以下为**可测试的目标建议**，应在开发初期通过用户设备基准后锁定具体阈值：

- 2×2 / 3×3 矩阵运算可在公式、平铺和层叠三种视图联动；选中元素能够反查到具体公式与 trace 步骤。
- 对基础算子集合，前向和反向输出通过固定测试夹具；梯度检查能在规定容差内通过，并明确列出不支持算子。
- 逐步模式下每一步有稳定 `stepId`、输入/输出、shape/dtype/status；暂停动画不修改运行值。
- 可复现一次运行：同项目版本、参数和固定随机种子产生相同的结构化 trace（允许在文档标注的浮点/后端差异范围内有数值差异）。
- 任一算法模板可在不打开主画布的情况下由 Debug Harness 独立执行。
- Presentation IR 可以脱离真实 kernel 用 fixtures 生成，且不需要 DOM 以外的计算副作用。
- 所有主操作可键盘访问；颜色不是区分类型/梯度的唯一通道。
- 在无网络环境下，已安装版本可以打开、保存、运行、调试和导出本地项目。

### 17.3 可观测性与诊断

默认只做本地日志；用户显式选择导出诊断包时，提供脱敏预览，允许排除项目数据和变量值。诊断包可包含 app 版本、平台、后端能力、发生错误的算子 ID、最小 trace、堆栈和许可证清单版本。不要默认把用户的公式、模型参数和项目文件上传到任何服务器。

## 18. 分阶段路线图

以下是面向大型跨职能团队的**规划估算**，不是承诺工期。各阶段允许部分并行，但必须以可验证的交付和退出条件控制范围。你的选择是“首发核心纳入自动求导”，因此自动求导不是第二阶段功能：第一版就必须具备真实的 VJP 规则和梯度校验。

### Phase 0：产品与架构验证（建议 3–4 周）

**目标：** 验证“结构化公式 → 数值执行 → trace → Presentation IR → 2D/3D 视图 → 基础梯度”能够贯通。

交付：
- Math IR、算子注册、Execution Trace、Presentation IR 四份 RFC；
- 2×2 矩阵乘法与标量函数 `f(x)=x^2` 的端到端 vertical slice，其中后者完成一次真实的前向/反向传播；
- Rust/WASM 与 TypeScript 参考实现的正确性对照；
- 主工作台 Figma/可交互原型和本地项目格式 spike；
- 5–8 名学生/工程师的任务测试。

退出标准：至少 80% 受试者能在没有口头指引的情况下完成“构建/运行公式、定位中间结果、查看梯度来源”三项任务。该指标是待验证的产品假设，不是市场事实。

### Phase 1：首发 MVP——数学工作台 + 自动求导（规划 4–6 个月）

**目标：** 做出一个范围有限、数学语义真实、可调试、可视化联动的本地应用；线性代数是基础数值域，自动求导是首发重点闭环。

交付：
- Windows/macOS 安装包、离线运行、本地 `.mathproj` 项目保存/恢复、自动保存、撤销/重做；
- Math IR、Scalar/Vector/Matrix/Tensor 的基础类型与 shape 检查；LaTeX 输入、符号 palette、拖拽吸附和结构化公式组块；
- 有限但真实的算子集：`add/sub/mul/div/sin/cos/exp/log/relu/sum/mean/matmul/transpose/reshape/slice`；
- 反向模式 tape/DAG、VJP 规则、梯度累加、固定夹具与有限差分梯度检查；明确显示不可微节点和不支持规则；
- Execution Trace、函数单独运行、输入夹具、断点、watch、单步/暂停/继续/重播、trace 导出；
- 2D 矩阵/张量切片观察器与可折叠 Z 轴步骤堆叠视图联动；循环可以折叠，但逐次执行记录真实保留；
- 内置入门项目：`y=Ax`、简单损失函数和一个小型 MLP 的前向与梯度示例（不承诺通用 ONNX 导入）；
- Linux 保持可构建与 CI 冒烟，正式支持取决于后续兼容性门禁。

退出标准：基础算子前向/梯度测试通过；视图切换不触发重复计算；用户可从损失追踪某个输入或权重的梯度来源；项目能离线保存和恢复；关键操作有键盘路径且颜色不是唯一语义编码。

### Phase 2：精度实验室与自动求导扩展（规划 2–3 个月）

交付：
- FP64/FP32 参考路径与 FP16/BF16/FP8/FP6/FP4/MXFP4 的编码、舍入和量化模拟；明确区分格式编码、缩放、累加 dtype、执行后端及“原生/模拟”状态；
- 误差分布、NaN/Inf、溢出/下溢统计与不同精度的并排观察；
- JVP、向量函数 Jacobian 的分块计算、更多梯度规则和边界条件；
- WASM SIMD/多线程基准；按能力探测增加可选 WebGPU 路径，保留 CPU/WASM fallback；
- 大型 trace 的采样、聚合和局部捕获。

退出标准：每种格式的模拟/原生语义都有文档和测试；性能报告记录设备、版本、shape、dtype、误差与执行后端。

### Phase 3：微积分、算法模板与优化（规划 3–4 个月）

交付：偏导、梯度、Jacobian/JVP 观察器；梯度下降、最小二乘、线性方程组、LU/QR；排序、堆、BFS/DFS 等算法结构；算法模板统一包含公式、可执行 DAG、参数 schema、复杂度说明、测试夹具和可视化 preset。

退出标准：新增算法不另建独立执行/表示管线；同一算法模板可以独立调试，也可作为子图嵌入更大工作流。

### Phase 4：神经网络与模型互操作（规划 2–3 个月）

交付：ONNX 前向导入、权重/激活/精度观察器、网络层 Z 轴堆叠；将外部模型节点尽可能映射回内部 IR；对于不支持或不透明的算子明确显示黑盒边界。训练流程和优化器以经过验证的有限子集扩展，不在该阶段承诺通用框架兼容。

退出标准：导入模型的支持矩阵、后端 fallback 和数值差异清楚可见；每个被支持的算子都有一致性测试。

### Phase 5：生态与正式 Linux 支持（持续阶段）

交付：Linux 正式发布门禁、模板包分发、版本化插件 API、可选 Python 互操作、文档/教程/示例项目、社区贡献与安全治理。云同步不是当前产品前提；任何未来服务都不得破坏本地优先和核心功能免费原则。

退出标准：第三方模板/插件在权限受控环境运行，依赖许可证和 SBOM 可追踪，发布有兼容性矩阵、安全响应和长期维护机制。

## 20. 主要风险、待验证假设与决策清单

### 20.1 主要风险

| 风险 | 影响 | 缓解方案 |
|---|---|---|
| 首版范围过大 | 自动求导、3D、公式编辑、精度系统并行，可能拉长周期 | 用 2×2 matmul 作为 vertical slice；先做有限但真实的 AD 算子集 |
| IR 过度设计 | 通用性高但无法交付 | schema 版本化，按真实用例演进；任何抽象都需由至少两个具体消费者验证 |
| 3D 视图喧宾夺主 | 学习者不理解流程或被视觉复杂度压制 | 让 2D/3D 视图可切换；初次运行默认简单布局；支持减少动态效果 |
| 低精度命名误导 | 用户把软件模拟误认为硬件原生算术 | 数据格式与执行后端分开建模，UI 明示“原生/模拟/量化” |
| 大矩阵 trace 爆炸 | 内存与 UI 卡顿 | trace policy、聚合步骤、局部捕获、虚拟化和大块数据按需读取 |
| 数值稳定性与梯度边界 | 结果看似正确但在边界条件错误 | 测试夹具、有限差分、误差面板、不可微标签、双精度参考路径 |
| 开源依赖许可冲突 | 影响分发/商业使用 | SPDX/SBOM、许可证扫描、人工审查第三方资产与内容 |
| Electron 安全与插件风险 | 本地文件和系统权限暴露 | 最小权限 IPC、沙盒、严格 CSP、插件隔离、恶意项目测试 |
| 性能跨平台差异 | 机器/驱动上体验不一致 | CPU/WASM fallback、能力检测、可复现基准和兼容矩阵 |

### 20.2 待验证假设

1. 用户是否会把“3D 层叠视图”作为常用主视图，还是主要用来展示/讲解？
2. 符号拖拽与吸附是否比输入 LaTeX/快捷键更高效？两种方式应如何平衡？
3. 普通学习者能否理解颜色编码的矩阵/标量/梯度语义？颜色是否需默认减弱？
4. 哪些计算步骤值得生成微观 trace？是否能用简单规则自动选择观察粒度？
5. 首发用户更常用纯鼠标拖拽、键盘快捷键，还是 LaTeX 编辑？
6. 对于神经网络目标用户，是否必须在首版就支持模型导入，还是清楚透明的手工搭建案例更能展示产品价值？
7. 开源维护模式能否持续支持跨平台发布、数学内容审核和安全修复？需要资助/赞助计划实测。
